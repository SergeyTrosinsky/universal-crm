# Universal CRM

Универсальная CRM: FastAPI + SQLAlchemy 2.0 + Jinja2/Tailwind. Кастомные поля (EAV) и статусы настраиваются в UI без правки кода.

## Запуск
```powershell
python -m venv .venv
.venv\Scripts\activate                      # Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt
copy .env.example .env                      # Linux/macOS: cp .env.example .env
python -m app.cli create-admin --email admin@company.com --name "Иван Петров"   # спросит пароль
uvicorn app.main:app --reload               # http://127.0.0.1:8000  (Swagger: /docs)
pytest
```
Первого администратора можно не создавать вручную: задайте `FIRST_ADMIN_EMAIL` / `FIRST_ADMIN_PASSWORD`
в `.env` — он появится при старте, если в БД ещё нет пользователей.

`DATABASE_URL`: `sqlite:///./crm.db` (по умолчанию) или `postgresql+psycopg2://user:pass@host:5432/crm`.

## Архитектура
`api/` и `web/` (HTTP) → `services/` (бизнес-логика, EAV) → `models/` (SQLAlchemy) → `db/`.

## Авторизация и права
- Вход: `/login` (HTML) или `POST /api/v1/auth/login` (JSON). JWT лежит в HttpOnly-cookie (`SameSite=Lax`)
  либо передаётся заголовком `Authorization: Bearer ...`.
- Токен привязан к отпечатку пароля: смена пароля и отключение пользователя сразу обесценивают старые токены.
- Роли хранят список прав (`app/core/permissions.py`), `*` — полный доступ. Роли и пользователи
  редактируются в разделе «Настройки» (`/settings/users`, `/settings/roles`) или через API.
- Защиты: нельзя отключить/понизить себя, нельзя оставить систему без администратора,
  пользователь без полного доступа не может выдать роль администратора.

## Настройка CRM под себя (без правки кода)
Раздел «Настройки» (право `settings:manage`):
- **Поля** — `/settings/fields` (API: `/api/v1/custom-fields`). Для клиентов и сделок можно создавать поля
  12 типов: текст, многострочный текст, целое, дробное, дата, дата и время, да/нет, список, множественный список,
  телефон, email, ссылка. У поля есть флаги «обязательное», «фильтр в списке», «колонка в списке», «активно»;
  порядок меняется стрелками (API: `POST /custom-fields/reorder`). Код и тип поля после создания не меняются;
  скрытие поля (`is_active=false`) не удаляет введённые значения, удаление — удаляет.
- **Статусы сделок** — `/settings/statuses` (API: `/api/v1/statuses`): название, цвет `#RRGGBB`, порядок и тип
  (`open` / `won` / `lost`). Тип определяет `closed_at`: открытые сделки не закрыты, выигранные и проигранные получают
  дату закрытия. Всегда есть ровно один статус «по умолчанию»; статус, используемый сделками, удалить нельзя (только скрыть).
- **Готовые наборы** — кнопки «Автосервис» и «Салон красоты» на странице полей добавляют типовые поля и статусы
  (повторное применение ничего не дублирует).

## Клиенты и сделки
- `/clients`: список с пагинацией (20 на страницу), сортировкой, поиском по имени, компании, email, телефону
  (в том числе по цифрам), адресу и **текстовым значениям кастомных полей** (VIN, госномер…),
  фильтрами по типу, ответственному и по любому полю с флагом «фильтр».
- `/deals`: список с суммами по валютам, фильтрами по статусу, типу статуса, клиенту, ответственному, датам, суммам
  и кастомным полям; карточка сделки со сменой статуса; создание из карточки клиента.
- Форма строится из активных полей: тип поля определяет элемент ввода (дата, число, список, флажок…).
- API: `GET /api/v1/clients|deals` с теми же параметрами, `cf_<код>=значение`, для чисел и дат —
  `cf_<код>__from` / `cf_<код>__to`. В теле запросов кастомные значения передаются в `custom: {"vin": "..."}`;
  `PATCH` меняет только присланные ключи, `null` очищает значение, неизвестный ключ даёт `422` (`custom.<код>`).
- Поиск на SQLite нечувствителен к регистру и для кириллицы.

## Задачи и главная страница
- **Задачи** — `/tasks` (API: `/api/v1/tasks`): название, описание, срок (дата и время), приоритет, статус
  (к выполнению / в работе / выполнена / отменена), исполнитель, привязка к клиенту и/или сделке
  (если выбрать сделку, клиент подставится из неё). Вкладки «Открытые / Просроченные / На сегодня / Закрытые / Все»
  со счётчиками, поиск, фильтры по статусу, приоритету, исполнителю и сроку; галочка в списке отмечает задачу выполненной.
  Блок «Задачи» есть в карточках клиента и сделки.
- **Видимость**: без права `tasks:read_all` сотрудник видит только задачи, где он исполнитель или автор
  (чужие отдают 404). С правом — задачи всех сотрудников (фильтр «Исполнитель»).
- **Главная** — `/` (API: `GET /api/v1/dashboard?period=7|30|90|365|all`, право `dashboard:read`):
  сделки в работе, выиграно / проиграно и конверсия за период, суммы **раздельно по валютам**, распределение
  по статусам воронки, динамика за 6 месяцев, таблица сотрудников, мои задачи и просрочки, последние сделки и клиенты.
  Блоки показываются только тем, у кого есть право на соответствующий раздел.
- **Разбивка по вашим полям**: для каждого активного поля-списка (например, «Мастер», «Услуга», «Марка авто»)
  на главной автоматически появляется распределение по значениям — без правок кода.

## Миграции базы данных (Alembic)
Схему ведёт Alembic (`alembic/versions`), строка подключения берётся из `DATABASE_URL`.
```powershell
alembic upgrade head                         # применить все миграции (новая БД, в т.ч. PostgreSQL)
alembic revision --autogenerate -m "описание"   # после изменения моделей: создать ревизию, проверить её глазами
alembic downgrade -1                         # откатить последнюю
```
- **Разработка**: `AUTO_CREATE_SCHEMA=true` (по умолчанию) — таблицы создаются при старте, миграции не обязательны.
- **Продакшен**: `AUTO_CREATE_SCHEMA=false` в `.env` и `alembic upgrade head` при каждом обновлении.
- **У вас уже есть `crm.db`, созданная без Alembic** (схема совпадает с начальной ревизией): один раз выполните
  `alembic stamp head` — база будет помечена как актуальная, дальше работайте через миграции.
- Тест `tests/test_migrations.py` применяет миграции к чистой базе и сверяет результат с моделями:
  если вы изменили модель и забыли ревизию, он упадёт.

## Доска сделок (канбан)
`/deals/board` — колонка на каждый активный статус воронки (отключённый статус показывается, пока в нём есть сделки):
число сделок и суммы по валютам в заголовке, поиск, фильтры по ответственному и клиенту, до 50 карточек в колонке
(остальные — ссылкой «открыть списком»). Карточку можно перетащить в другую колонку — статус меняется через
`POST /api/v1/deals/{id}/status`, при ошибке карточка возвращается назад с сообщением. На сенсорных экранах
в карточке есть выпадающий список статусов. Без права `deals:write` доска работает только на просмотр.

## Общие настройки (под вашу отрасль)
`/settings/general` (API: `GET/PATCH /api/v1/settings/general`, право `settings:manage`): название CRM, валюта по умолчанию
для новых сделок и **термины** — как система называет клиентов и сделки (например, «Пациенты» и «Приёмы»).
Термины задаются в трёх формах (мн. число, ед. число, винительный падеж для «Добавить …») и подставляются в меню,
списки, формы, карточки, доску и главную страницу. Готовые наборы («Автосервис», «Салон красоты») при применении сами
подставляют подходящие термины («Заказы», «Записи»), если вы ещё не меняли их вручную.
Настройки хранятся в таблице `app_settings` (миграция `0002`).

## Роли: кто что видит и назначает

| Роль | Сделки | Задачи | Статистика |
|---|---|---|---|
| Сотрудник | только свои (где он ответственный), ответственного не назначает | свои, ставит только себе | личная |
| Менеджер | все; назначает ответственных | все; ставит задачи сотрудникам | общая и по сотрудникам |
| Администратор | всё, включая настройки и пользователей | всё | общая |

Это набор прав (`deals:read_all`, `deals:assign`, `tasks:assign`), поэтому поведение любой роли меняется в
Настройки → Роли без правки кода. Менеджерам существующей базы эти права добавляются автоматически один раз при запуске.

## Шаблоны сделок (заказов, записей)

Настройки → **Шаблоны**. Шаблон — именованный набор дополнительных полей (например, «Автосервис»: Марка авто,
VIN, Госномер). При добавлении записи вверху формы выбирается «Стандартная форма» или шаблон, и показываются
общие поля плюс поля выбранного шаблона. Поле без шаблона — общее. Привязка делается в форме поля («Шаблон»).
Готовые наборы («Автосервис», «Салон красоты») создают шаблон сами. Шаблон с полями или записями удалить нельзя —
его можно скрыть. API: `/api/v1/deal-templates`, поле `template_id` у сделок и полей.

Применить миграцию: `alembic upgrade head` (ревизия `0003`).

## Импорт и экспорт (Excel и CSV)

В списках «Клиенты» и «Сделки» есть меню **Импорт / экспорт**.

- **Шаблон файла.** «Загрузить из файла» → «Шаблон Excel» или «Шаблон CSV». Заголовки совпадают с вашими полями,
  включая дополнительные; в Excel есть лист «Подсказки» и выпадающие списки (статусы, шаблоны, значения полей).
  Порядок колонок не важен, ненужные можно удалить, названия находятся без учёта регистра.
  Если подпись поля повторяется или совпадает со стандартной колонкой, к ней добавляется код: «Мастер (master)».
- **Загрузка с проверкой.** Сначала вы видите предпросмотр: сколько записей будет создано, обновлено, пропущено и
  ошибки по строкам (номер строки, что не так). Пока вы не нажали «Загрузить», в базу ничего не пишется.
  Строки с ошибками не загружаются, остальные загружаются. Проверка идёт теми же правилами, что и форма
  (обязательные поля, типы, списки, статусы, шаблоны, права).
- **Клиенты.** Повтор ищется по email и телефону (8 916… и +7 916… — один номер). Повторы либо пропускаются,
  либо обновляются: заполненные ячейки заменяют значения, пустые ничего не стирают.
- **Сделки.** Клиент находится по «Телефон клиента» или «Email клиента» и должен уже быть в CRM: сначала загрузите
  клиентов. Статус, шаблон и ответственный указываются названием (ответственный — email или ФИО). Поля шаблона
  заполняются только у записей с этим шаблоном. Права те же, что в форме: сотрудник без права назначать может
  загрузить только свои записи.
- **Выгрузка.** «Excel» или «CSV» из меню берёт текущий список с фильтрами и поиском, без разбивки на страницы
  (до 50 000 строк). Сотрудник выгружает только свои сделки. Файл можно поправить и загрузить обратно.
- **Форматы.** CSV в UTF-8 с разделителем «;» открывается в русском Excel двойным кликом; при загрузке понимаются
  также Windows-1251, «,» и табуляция. Текст, похожий на формулу (`=…`, `@…`), в выгрузке получает апостроф, чтобы
  Excel не выполнил его как формулу; при загрузке апостроф снимается.

Лимиты: `IMPORT_MAX_ROWS` (5000 строк), `IMPORT_MAX_FILE_MB` (5 МБ), `IMPORT_DIR` (куда на 2 часа кладётся загруженный
файл до подтверждения; по умолчанию временная папка). Нужен пакет `openpyxl` (есть в `requirements.txt`).

- **Повторная загрузка сделок.** По умолчанию строка пропускается, если такая сделка уже есть (совпали клиент, название, сумма, валюта и дата) — так двойная загрузка одного файла ничего не дублирует. Для случая, когда одинаковые записи — это разные записи, на странице загрузки есть вариант «Загрузить всё равно».

## История изменений и заметки

В карточке клиента и сделки внизу есть лента «История и заметки»:

- **История** пишется автоматически: кто и когда создал запись и что изменил — было → стало. Попадают поля формы, статус, сумма, дата, ответственный, шаблон и значения ваших дополнительных полей (в том числе при смене статуса на доске, через API и при импорте в режиме «Обновить»). Если форму сохранили без изменений, запись не создаётся.
- **Заметки** — свободные комментарии сотрудников. Добавлять их может тот, кто имеет право редактировать клиентов (для сделок — сделки) и видит эту карточку. Заметку удаляет её автор или администратор.
- Журнал и заметки удаляются вместе с карточкой. Имя автора хранится в самой записи, поэтому после удаления пользователя оно остаётся.
- API: `GET /api/v1/clients/{id}/activity`, `POST /api/v1/clients/{id}/notes`, `DELETE /api/v1/clients/{id}/notes/{note_id}` и то же для `/deals/{id}/…`.
- Таблицы создаёт миграция `0004`: `alembic upgrade head`.

## Windows: запуск и администрирование

- `run.bat` — запускает CRM в Docker и публичный туннель Cloudflare, открывает ссылку в браузере.
- `admin.bat` — меню: сохранить версию и отправить на GitHub, история и откат кода, резервная копия и восстановление базы, запуск/остановка/обновление контейнеров, тесты.

## Docker: запуск на сервере

Пошаговая инструкция для нового сервера (в т. ч. домен, HTTPS, копии вне сервера): **[DEPLOY.md](DEPLOY.md)**;
быстрый запуск — `bash docker/setup.sh`, обновление — `bash docker/update.sh`.

В комплекте: `Dockerfile` (приложение), `docker-compose.yml` (приложение + PostgreSQL + автоматические
резервные копии + по желанию HTTPS через Caddy). Миграции применяются сами при каждом старте контейнера.

**Первый запуск** (на сервере с Docker и Docker Compose):
```bash
cp docker/env.example .env.docker
# заполните POSTGRES_PASSWORD и SECRET_KEY (openssl rand -hex 24 / -hex 32), пароль первого администратора
docker compose --env-file .env.docker up -d --build
docker compose --env-file .env.docker logs -f app        # дождитесь «Запускаю сервер»
```
CRM откроется на `http://127.0.0.1:8000` (на самом сервере). Проверка: `curl http://127.0.0.1:8000/health`.

**С доменом и HTTPS.** Направьте A-запись домена на IP сервера, в `.env.docker` задайте `DOMAIN`,
`AUTH_COOKIE_SECURE=true`, `TRUST_PROXY_HEADERS=true` и запустите с профилем:
```bash
docker compose --env-file .env.docker --profile https up -d --build
```
Caddy сам получит и будет продлевать сертификат; порты 80 и 443 на сервере должны быть открыты.
**Без домена** можно открыть порт приложения (`APP_BIND=0.0.0.0`), но трафик пойдёт без шифрования —
для интернета так не оставляйте.

**Резервные копии.** Сервис `backup` делает копию базы при старте и затем каждые `BACKUP_INTERVAL_HOURS`
часов в папку `./backups` (формат `crm_ГГГГММДД_ЧЧММСС.dump`), каждая проверяется на читаемость, старше
`BACKUP_KEEP_DAYS` дней удаляются. Копии лежат на том же сервере, поэтому периодически копируйте папку
`backups` в другое место (другой сервер, облако) — иначе потеря сервера уничтожит и данные, и копии.
```bash
docker compose --env-file .env.docker logs backup                 # журнал копирования
bash docker/restore.sh backups/crm_20261008_030000.dump              # восстановить базу из копии
```

**Обновление версии:**
```bash
git pull   # или загрузите новые файлы на сервер
docker compose --env-file .env.docker up -d --build              # миграции применятся сами
```
**Служебные команды:**
```bash
docker compose --env-file .env.docker exec app python -m app.cli create-admin --email a@b.ru --name "Имя"
docker compose --env-file .env.docker exec app python -m app.cli reset-password --email a@b.ru
```
Данные хранятся в томах Docker (`pgdata` — база, `app_data` — временные файлы импорта); команда
`docker compose down` их не удаляет, а `down -v` — удалит.

Приложение запускается одним процессом (`--workers 1`): счётчики неудачных входов хранятся в памяти.
Нагрузка в сотни пользователей для одного процесса не проблема; для нескольких процессов их сначала
нужно вынести в общее хранилище.

Миграции на настоящем PostgreSQL проверяет отдельный тест `tests/test_postgres_migrations.py`
(запускается, только если задан `TEST_POSTGRES_URL`, см. комментарий в файле).

## Безопасность

- **CSRF.** Каждая форма автоматически получает скрытое поле `csrf_token`, а запросы из JavaScript
  (перетаскивание на доске) — заголовок `X-CSRF-Token`. API по cookie без токена отвечает 403;
  вход через `Authorization: Bearer …` токена не требует. Токен меняется при входе и выходе.
- **Подбор пароля.** После `LOGIN_MAX_ATTEMPTS` неудачных входов на один email (или
  `LOGIN_MAX_ATTEMPTS_PER_IP` с одного IP) за `LOGIN_WINDOW_SECONDS` вход блокируется: страница
  отвечает 429 с подсказкой «повторите через N мин.», API — 429 и заголовком `Retry-After`.
  Успешный вход сбрасывает счётчик. Счётчики хранятся в памяти процесса.
- Пароли хешируются bcrypt, сессия — подписанные HttpOnly-cookie с `SameSite=Lax`.
  В продакшене задайте `SECRET_KEY` и `AUTH_COOKIE_SECURE=true` (HTTPS).
